# Learnings Folder

This folder contains documented findings from feasibility studies, proofs of concept, and probing experiments.

## Naming Convention
`XXX-finding-descriptive-name.md` — three-digit sequential numbering shared across `plans/`, `probing/`, `poc/`, `fixtures/`, `learnings/`.

## Template
Each learning document should include:
1. **Date** — when the study concluded
2. **Study Context** — what was being evaluated and why
3. **Summary** — one-line conclusion
4. **Key Findings** — detailed evidence, organized by topic
5. **Recommendation** — go/no-go with rationale
6. **Next Steps** — concrete actions (new probing, PoC, plan updates)
7. **References** — links to sources, PRs, docs, code

- [009 — Specialized Decision & Classification Models vs Generative LLMs](009-decision-classification-models.md) — Desk study + live probes of OpenRouter's Decisions/Extractions categories ($0.0006 spent). Decisions return typed judgments, not values — the alpha API 400s on any value-typed field; `choice`/`noul` classify Hindi/Telugu well (language survives p=0.45 corruption). Paid probe: clairic/ScaleDown extract Indic values from *text* (5/5, 4/5) but **neither reads a Telugu scan** — the OCR bypass is closed. Recommendation: keep the generative LLM as extractor; decision models only as a calibrated *validator* behind a measured gate.
- [011 — Deployment Exposure Audit & Single-Origin Fix](011-deployment-exposure-and-single-origin.md) — Prod was undeployable since the auth commit (two `:?` env vars missing from Dokploy → 404), and once up every mutation 403'd because the API sat on its own subdomain (host-only CSRF cookie unreadable by the frontend). - [012 — Moderated Signup, Admin-Only Library, Owner-Only Book Access](012-moderated-signup-outcome.md) — Shipped `plans/007`: additive `account_status` migration (backfills `approved`), a router-level `require_approved_user` gate (pending/rejected → 403, `/auth/*` stays open for the holding screen), admin approve/reject endpoints + pending-count badge, and removal of the public catalog (Library is admin-only; book detail/thumbnails are owner-or-admin, non-owner 404). - [013 — Verified-GT Shortlist, OCR Variant & Recall Diagnosis](013-verified-shortlist-and-ocr.md) — 35/35 books source-verified; on verified books **phi4-mini F1 0.333 ≫ qwen3-4b-instruct-2507 0.106** (confirms 010, contradicts 005); `tessdata_best` Telugu CER 0.419 vs 0.453 (marginal); recall failures = null-returns + a schema-echo bug (`title="CoreIdentityBatch"`); oki Ollama capped at 6 GiB.
- [014 — Frontend + Backend Route Redesign Outcome](014-routing-redesign-outcome.md) — Retired `/api/library/*` (catalog → `GET /api/admin/books` + `/api/admin/filters`; detail → `GET /api/books/{id}/detail`), grouped dashboard/job routes under `/api/dashboard` (cancel → `POST /api/dashboard/jobs/{id}/cancel`), and moved the bulk page `/bulk-operations` → `/admin/bulk`. - [015 — Service Inventory, Memory Profile & Non-Essential Gating (oki)](015-service-inventory-and-gating.md) — Non-essential services idle at **2522 MiB (16% of RAM)** — openrefine 1084 + elasticsearch 900 dominate — while a core-only stack runs at 1422 MiB. `COMPOSE_PROFILES` gating verified end to end with no restructuring (boolean `ENABLE_*` is not native to Compose, and runtime flags can't drive Next's build-time-inlined UI). Under load the pipeline peaks at 7713 MiB anon / 3070 MiB available, so **extraction wall-clock (81% of per-book vs OCR 19%) is the real constraint, not RAM**. Gating not yet implemented.
- [016 — The Pipeline Could Not Process a Book at HEAD](016-pipeline-non-functional-at-head.md) — Three layered defects made end-to-end processing impossible: stage tracking broken **five ways** (every transition raised), a preprocessing guard that matched the job that dispatched it (**OCR dead since 2026-09-01**), and an LLM persistence **self-deadlock** (KEY SHARE vs FOR UPDATE across two sessions) that hung silently at `running 100%` with zero rows written. All three fixed and verified to `awaiting_review`; 15+5 failing tests restored, 9 new stage tests added.
- [017 — Self-Hosted LLM Configuration: Parameter Reference & Evidence Base](017-llm-configuration-research.md) — Model/inference/runtime parameter reference with defaults, CPU/RAM impact and evidence. Measured calls are **0.9–1.4 K prompt + 53–70 output tokens**, so context is not the constraint — RAM residency, generated tokens and threads are. Provisional profile: `phi4-mini` or `gemma4:e4b` + `think:false`, Q4_K_M, ctx 4096–8192, **temp 0**, pinned seed, `num_predict` 512, `repeat_penalty` 1.0, 3 threads, 1 parallel, f16 KV, 6 GiB cap. Config conflicts found: ctx 8192 vs 4096, app parallel 2 vs server 1, max_tokens 256 vs 512.
- [018 — LLM Configuration Validation: Parameter Matrix on Verified Telugu Books](018-llm-config-validation.md) — 32-call matrix on `test-node-2`: **`gemma4:e4b` `think:false` F1 0.82/0.73 ≫ `phi4-mini` 0.35/0.44** (and phi4-mini **looped into invalid JSON** despite schema-constrained decoding). ctx 4096 ≡ 8192; temp 0 byte-identical across seeds; `repeat_penalty` 1.1 no help; 4 threads no help; **prompt-prefix caching ≈ 4× speedup**; no memory pressure (≥2.8 GiB free). Adopt **ctx 4096** + a repetition/loop guard.
- [019 — Enriching the Ground-Truth Corpus](019-gt-corpus-enrichment.md) — The empty fields were missing from the *sources*, not our extraction: added 14 CC/PD Hindi books (corpus → 30 tel / 19 hin), deepened catalog reads (Commons categories, IA subject/publisher, `ISBN` + Hindi Wikisource labels), and filled the scan-embedded fields with a node OCR+LLM pass. Coverage **308 → 623** non-null fields, **12 → 37 / 49** distinct fields populated; the fill run is 49 books in ~2 h. Key finding: `think:false` is ignored via the OpenAI-compatible endpoint (gemma4 returns empty content) and must use native `/api/chat`.
- [022 — Ground-Truth Source Expansion: scale, catalogue depth, script fix](022-gt-source-expansion.md) — Corpus **49 → 71 books** (+22 CC/PD Telugu/Hindi, 844 values). Catalogue adapters added little: Pustaka Nidhi matched 17 books whose titles were already Telugu; IA `dc.*` was already captured; the 22 new Commons-only books have **no IA id**, so identifier-keyed catalogues can't reach them. - [024 — Host Network Recovery & gemma4 Resource Reality](024-host-network-and-gemma-resource-reality.md) — oki egress is **fixed** (PyPI 32 MB/s, HF 1.1–2.3 MB/s, registry pulls work) so no container-registry bypass is needed; **ingress is still open** (origin answers 200 with the real Host header). `gemma4:e4b` is **6.6 GB / 7.5B** and peaks at **7.9 GiB**, so the Ollama cap moved to 9 GB. Telugu OCR weights are **310 MB**, not 1.7 GB. The Debian/PyPI mirror workaround was removed from the Dockerfile.
- [025 — Prompt Engineering for 49-Field Metadata Extraction](025-prompt-optimization.md) — Existing prompts have **two contradictory null rules**, no per-field guidance, a synthetic few-shot example injected into batches it does not fit, and no conflict/script policy. Built 13 profile variants behind a production-compatible registry (**byte-identical baseline**), a mask-aware harness that separates prompt defects from routing defects and catalogue-only ground truth (**99.6 %** agreement with human verification), and value-level metrics with paired bootstrap CIs. **Accuracy arms not yet run** — no outcome claim. Clean control track is **Telugu-only, 17 books** (13 of 30 Wikisource files have empty `pages`).
- [026 — Review of the Hindi/Telugu OCR Improvement Strategy](026-ocr-accuracy-strategy-review.md) — Audited the four-pillar strategy against code + benchmarks. Cited numbers hold (Telugu 0.163/0.402; Hindi 0.072 — but on **IndicVisionBench, not our books**). Real blockers found: `OCR_CUSTOM_MODEL_DIR` and `OCR_AUTO_PREPROCESS` are **declared but never read**, `train_tesseract_lstm.sh` passes invalid `tesstrain.sh` flags (and ignores `--epochs`), `GET /api/admin/ocr-corrections` **does not exist**, and `corrections` stores only rule firings. Rejected as damaging: shirorekha removal, numeral→word normalization, MBART/ByT5 correction of proper nouns. Surya's "llama.cpp CPU backend" claim is unsupported. OCR is **19 % of per-book wall-clock** (LLM 81 %), so a Hindi fine-tune is not the top-ROI first move. Plan: [plans/019](../plans/019-ocr-accuracy-improvement.md).
- [027 — Default Preprocessing Is a 1.5× Upscale, and It Costs Accuracy](027-default-preprocessing-upscale-benchmark.md) — Pages are rendered at 300 DPI, then `upscale_to_dpi(current_dpi=200)` rescaled them to **450 DPI** while Tesseract was told `--dpi 300`. On 18 paired Telugu pages that cost accuracy: median CER **0.365 vs 0.285** with the upscale off (worse on 15/18 pages, mean +0.027) and 2.25× the pixels. `deskew`, `remove_borders` and `grayscale` are **inert** on these scans (identical output on all 18 pages), so the entire default pass was the harmful upscale. Fixed via `run_pipeline(source_dpi=...)` defaulting to `OCR_RENDER_DPI`; re-run now matches `no_upscale` exactly (median 0.285). Confirmed on the line model in [028](028-line-model-preprocessing-benchmark.md).
- [028 — The Telugu Line Model Does Not Want the 1.5× Upscale Either](028-line-model-preprocessing-benchmark.md) — Closed 027's open question on the engine production actually ships: on the same 18 pages, `pipeline_default` leaves median CER unchanged (0.174 vs 0.174 raw, 12/18 byte-equal, 4 worse/2 better) while the legacy 450-DPI path is worse (median 0.184, mean +0.012, 11/18 pages). So no engine-conditional upscale is needed — the global fix is correct for Tesseract *and* the line model. Also: preprocessing moves **line-segmentation boundaries** (line counts differ per variant), and the model's 2048-px width limit is hit by **4 crops in every variant**, so those lines are silently dropped until the split fix in [029](029-ocr-language-routing-and-font-benchmarks.md).
- [029 — Why the OCR Looks Wrong: Language Routing, the `+eng` Model, and Typeface Limits](029-ocr-language-routing-and-font-benchmarks.md) — Measured the current engines on 21 Telugu GT pages / 8 books and 24 Hindi IndicVisionBench pages. Telugu line model **0.163 CER** (Tesseract `tel` 0.382, `tel+eng` 0.331); Hindi `hin` **0.063** (`hin+eng` 0.081). The Latin fallback is an **integration** bug: global `tel+eng`/`hin+eng` puts **21 %** Latin into Telugu body and raises Telugu consonant errors 14.5→24.5 %; a line-model load failure falls back to `tel+eng` (13.7 % Latin, confidence 61); a Hindi book uploaded as Telugu scores **0.824 CER, 77 % Latin**. At study time uploads defaulted to tel and there was no edit path; the default is now removed, and a `PATCH /books/{id}/language` endpoint plus header control exist. Controlled fonts: Tesseract Telugu is already **0.153** on clean Noto; line model 0.084 oracle / 0.19–0.30 decorative; mild blur/contrast/DPI noise changed <0.02. The line model silently drops **>2048-px** crops; splitting recovered 1857 cover **0.880→0.025** and wide synthetic **0.548→0.203**. Conjunct clusters: 9.6 % (line) vs 35.5 % (`tel`) / 42.1 % (`tel+eng`); digits 44–67 %. Recommends page script routing, upload-language integrity, wide-line/coverage guards; no new engine, fine-tune only after routing. **Implemented:** wide-line split, empty-output fallback, explicit upload language, language PATCH + header control, Latin/dominant-script reroutes (Hindi median 0.090→0.061; 1857 cover 0.880→0.014), and `--tessdata-dir`; a line-count coverage threshold was tested and rejected. Plan: [plans/020](../plans/020-ocr-language-and-page-type-routing.md).

- [036 — pgvector Semantic Search: Why It Sat Unimplemented, What It Would Cost, and Its Removal](036-pgvector-removal.md) — It was provisioned as *future* infrastructure in 001 and never given a study, an embedding model or a caller (`plans/006` and `plans/008` both list it out of scope; nothing wrote or read the table). Sized: **+0.5–1.5 GB RSS and <0.1 % of per-book CPU** for a 768-dim MiniLM/e5 model, against **3.0 GiB** measured headroom — so it fits only via the worker (torch is already baked in for the Telugu line model), **not** via Ollama (`OLLAMA_MAX_LOADED_MODELS=1` makes search evict `gemma4`, 30–60 s reload). Storage 3 KB/book → 31 MB at 10k, ~600 MB HNSW at 100k; query <10 ms at 10k. **Removed as dead code:** model, `pgvector` dep, `embeddings` table + `vector` extension (migration `022`, `001` rewritten), image back to `postgres:16-bookworm`; `pg_trgm` kept.
- [037 — PostgreSQL 18 Upgrade (Fresh Volume)](037-postgres-18-upgrade.md) — With the app database disposable, the stack moves off the pgvector image to **PostgreSQL 18**: `postgres:18-trixie` in prod/staging, `postgres:18-alpine` in dev and CI. It is **not a tag swap** — PG18 images set `PGDATA=/var/lib/postgresql/18/docker` and declare `VOLUME /var/lib/postgresql`, so keeping the `pgdata:/var/lib/postgresql/data` mount puts the cluster in the container's writable layer and every recreate silently starts an empty database. The `backup` sidecar must move to `postgres:18-alpine` too, or `pg_dump` 16 refuses the 18 server. No dependency change: asyncpg **0.31.0** already supports 18 (tested in its changelog), and `pg_trgm` is bundled. Alpine (dev/CI) is musl and collates differently from glibc prod — harmless today, one-line fix if it bites.
